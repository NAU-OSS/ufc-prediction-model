# Contributing to UFC Prediction Model

Thanks for your interest in contributing to the UFC Prediction Model! Contributions of all sizes are welcome, including fixing bugs, improving documentation, adding statistics, or suggesting improvements to the prediction system.

## How to Contribute

Before making a contribution, check the existing issues and pull requests to make sure someone else isn't already working on the same idea.

For larger changes or new features, open an issue first to explain what you want to change and why. This gives others a chance to discuss the idea before you spend time implementing it.

For code changes:

1. Fork the repository.
2. Clone your fork to your computer.
3. Create a new branch for your changes.
4. Make your changes.
5. Test your changes locally.
6. Commit your changes with a clear commit message.
7. Push your branch to GitHub.
8. Open a pull request describing what you changed and why.

Pull requests should be focused on one change whenever possible. Please explain what was changed, how it was tested, and reference any related issues.

## Code Style

Try to keep the code consistent with the existing project.

* Use clear and descriptive variable and function names.
* Keep functions reasonably small and focused.
* Add comments when something may not be obvious to another contributor.
* Avoid unnecessary changes to unrelated parts of the project.
* Follow normal Python formatting conventions.
* Keep new code readable and simple.

Since this project uses statistics to make predictions, changes to the scoring system should also explain why the change was made and what effect it is expected to have.

## Testing

All changes should be tested before submitting a pull request.

For changes to the prediction model, test the model using an existing UFC card or test dataset and make sure the program produces valid predictions.

When possible, compare the updated model against previous results to determine whether the change affects prediction accuracy.

Pull requests should not knowingly introduce errors or break existing functionality.

## Documentation

Changes that affect how the project is used should also include updates to the documentation.

The README should remain accurate and should explain:

* What the project does.
* How to install it.
* How to provide fighter data.
* How to run the prediction model.
* How the prediction system works.

If you add a new feature or statistic, explain what it does and why it is being used.

## Reporting Bugs

If you find a bug, open a GitHub issue.

Please include:

* A description of the problem.
* The steps needed to reproduce it.
* What you expected to happen.
* What actually happened.
* Any relevant error messages.
* The CSV or input format being used, if applicable.

Before opening a new issue, check the existing issues to make sure the problem has not already been reported.

## Proposing New Features

New feature ideas are welcome. Open a GitHub issue and describe:

* What you would like to add.
* Why you think it would improve the project.
* How you think it could work.
* Any potential problems or limitations.

For major changes to the prediction system, it is helpful to discuss the idea in an issue before submitting a pull request.

## Community Guidelines

Please be respectful and constructive when communicating with other contributors.

* Assume good intentions.
* Keep discussions focused on improving the project.
* Give useful feedback instead of personal criticism.
* Be open to different ideas and approaches.
* Help new contributors when possible.
* Keep issues and pull requests professional and on topic.

Different opinions about the prediction model are expected. Discussions should focus on the code, data, and reasoning behind proposed changes rather than the people making them.

## Questions and Communication

For questions about the project, please use GitHub Issues so that other contributors can benefit from the discussion as well.

For security issues or other sensitive problems that should not be publicly discussed, contact the project maintainer directly.

## Pull Request Review

Pull requests will be reviewed based on whether they:

* Address the stated issue or goal.
* Follow the project's coding style.
* Include appropriate testing.
* Keep documentation up to date.
* Do not unnecessarily break existing functionality.

Not every proposed change will necessarily be accepted. Feedback may be requested before a pull request is merged.

Thank you for helping improve the UFC Prediction Model!
